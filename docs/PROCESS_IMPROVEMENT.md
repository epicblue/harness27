# Harness27 流程改进：数据采集与调查方案

本方案面向 Harness27 的上手、任务执行、审批体验、评测和文档流程改进。它提供一套低成本、可离线运行的混合方法：**客观任务指标 + 每任务短问卷 + 可选访谈**。目的是发现流程瓶颈，不是监视个人，也不把主观满意度当成模型能力或正确率。

当前仓库没有遥测/问卷采集服务。建议先手动或在本机整理脱敏摘要，不要为了收集数据而默认上传轨迹或增加后台遥测。

## 1. 先定义改进问题

每轮只聚焦一个可行动的问题，例如：

- 新用户是否能在不求助的情况下启动 Harness 并完成只读任务？
- 用户能否理解文件写入审批，并在不确定时安全拒绝？
- 哪些工具调用/协议错误导致任务失败或重试？
- benchmark 报告是否足以让操作者定位一次失败？
- 文档、服务配置还是模型/工具调用本身造成了最长等待？

为每个问题预先写出：目标用户/任务、固定版本和配置、主要指标、次要指标、停止条件、数据访问者与删除日期。避免看到数据后再临时改变“成功”的定义。

## 2. 推荐的单轮采集流程

### 第一步：选任务并固定基线

挑选 2–3 个有代表性的、可复现的任务，建议至少包含一个禁用 Shell 的只读任务；若要检查写入审批，使用无敏感数据的独立 workspace。Shell 任务只能在[外部隔离环境](SECURITY_OPERATIONS.md)中执行。固定 Harness commit、模型/服务配置标签、采样参数和任务版本；配置不一致的运行要分组，不要直接混算。

### 第二步：告知并取得同意

参与者在开始前看到一段简短说明：研究目的、会收集哪些摘要、不会收集哪些内容、谁能访问、保存多久、如何退出/撤回。参与完全自愿，不用于员工个人绩效评估。无需收集姓名、邮箱或其他身份信息；若确需纵向跟踪，用随机参与者代码，并把映射表与回答分开存放。

### 第三步：记录最小化的任务摘要

每次任务结束后，仅记录完成分析所必需的结构化字段（见下方模板）。优先使用 verifier、benchmark 汇总或本机人工计数；如果某项在当前工具中无法可靠取得，就留空并标记“未采集”，不要把原始轨迹复制到问卷表。记录模型配置时使用预先约定的短标签；详细部署配置单独受限保存。

### 第四步：每个任务后立即填写短问卷

在记忆尚清楚时填写第 5 节的 2–3 分钟问卷。每个 task ID 单独填一份，以便区分不同流程。问卷中明确标注“自我评价”；实际正确性另由 verifier 或独立检查记录。

### 第五步：可选的短访谈

对愿意参与的人进行约 15 分钟半结构访谈，追问“最近一次具体发生了什么”，不要只问笼统的“喜欢吗”。记录去身份化主题和简短摘要，不默认录音；如确需录音，应单独取得明确同意并设置更短的保留期限。

### 第六步：汇总、排序并做小改动

按任务类型/用户经验/配置分层查看结果，结合客观指标、量表分布和访谈主题。将发现整理为“问题—证据—影响—可能原因—改动—负责人—复测指标”。安全/隐私问题即使只出现一次也应优先处理；一般体验问题按频次、影响和修复成本排序。每轮尽量只改一个主要因素。

### 第七步：用相同任务复测

使用相同任务、同一组问卷题目和可比配置复测；记录 Harness commit 与服务端配置是否变化。比较中位耗时、成功/失败比例、评分分布和具体摩擦点。小规模试点只用于找问题和观察趋势，不应声称统计显著或普遍适用。

## 3. 建议收集的字段

### 任务摘要表（每行一个任务尝试）

```csv
study_id,session_id,participant_code,run_date_utc,harness_commit,model_config_id,task_id,task_category,task_outcome,independent_verification,elapsed_seconds,agent_steps,tool_calls,tool_errors,write_approval_requests,write_approvals,write_denials,shell_enabled,friction_tags
```

字段约定：

- `session_id` 使用随机 ID；`participant_code` 可选，若无需纵向比较则不收集。
- `task_outcome` 使用 `completed`、`partial`、`failed`、`aborted` 等预先约定的值；服务/协议异常另加 `infrastructure_error`，不要误记成模型任务失败。
- `independent_verification` 表示 `passed`、`failed`、`not_available` 等独立验证结果；用户“觉得做对了”不能替代它。
- `elapsed_seconds`、轮数和工具计数按同一口径记录；如果是人工估计，应注明来源/估计方式。
- `friction_tags` 从固定标签中多选，例如 `setup`、`tool_call`、`approval`、`latency`、`docs`、`reporting`、`safety_concern`、`other`。
- 不能可靠获得的指标留空并标记原因；不要为了填满表格而解析、导出或长期保存原始内容。

**不要收集：**原始任务提示词、完整模型回答、文件内容、Shell 命令/工具参数、reasoning、API key、绝对文件路径、完整 JSONL 轨迹或真实客户资料。若为了独立验证必须检查产物，应在本机受控环境检查，只汇总通过/失败和必要的错误类别。

## 4. 建议的问卷工具与采集方式

| 场景 | 建议工具 | 使用约束 |
|---|---|---|
| 离线或小规模试点 | 使用本页问卷的本地副本；每次任务一行 CSV/ODS，由受限目录中的 LibreOffice Calc 或组织批准的表格工具汇总。 | 文件不放进代码仓库；使用去身份化 ID；限制访问并按期限删除。 |
| 多参与者、重复试点 | 组织批准的自托管表单系统，开启匿名/最少字段模式，并只导出 CSV/JSON 汇总。 | 关闭非必要分析脚本/第三方追踪；确认数据实际存放位置、访问角色、备份和删除方式。若不能满足要求，退回本地表单。 |
| 运行指标 | 先从 benchmark 现有 JSON 报告或人工汇总中取得指标；必要时在本机生成最小摘要。 | 当前 Harness 没有默认遥测。不要把完整 trace 上传到表单平台；问卷与运行内容分开保存。 |
| 质性反馈 | 访谈者使用本地去身份化记录模板，或在获同意后写摘要。 | 不默认录音；不记录无关身份/敏感信息；引用前先脱敏并检查可识别风险。 |

**推荐起步选择：**离线试点用短问卷 + 本地 CSV/ODS；不需要开发新 Web 服务，也不引入新的运行时依赖。若参与者规模、匿名化或权限管理超出本地表格能力，再由组织批准后采用自托管表单。表格/表单是采集界面，不是自动遥测系统。

## 5. 可直接试用的任务后问卷

在问卷开头展示：

> 本问卷用于改进 Harness27 的任务流程。请勿填写任务中的密钥、文件内容、个人信息或完整提示词。参与自愿；结果以汇总形式用于改进，不用于个人绩效评价。你可以跳过任意题目。运行摘要与问卷通过随机 session ID 关联。

### A. 任务背景（不收集身份信息）

1. 你对本类任务的熟悉程度：`不熟悉 / 略熟悉 / 熟悉 / 很熟悉`。
2. 你此前使用 Harness27 的频率：`首次 / 偶尔 / 经常`。
3. 本次任务编号：从预先定义的 task ID 选择，不填写真实任务文本。

### B. 体验量表

统一选项：`1 非常不同意 / 2 不同意 / 3 既不同意也不反对 / 4 同意 / 5 非常同意 / 不适用`。

1. 我清楚如何开始这项任务。
2. 我能理解 Agent 当前在做什么，以及何时需要我作决定。
3. 工具审批让我能控制文件写入或命令执行。（没有审批时选“不适用”。）
4. 我能方便地判断任务结果是否满足要求。
5. 完成任务所需的等待时间和操作投入可以接受。
6. 遇到问题时，我知道下一步该检查什么。
7. 对于类似任务，我愿意再次使用这套流程。

这些是项目内部的**自定义脉冲题目，尚未经过心理测量学验证**。对单题报告评分分布/中位数即可；不要把分数称为 SUS/标准化可用性分数，也不要只用一个满意度总分代替客观任务结果。

### C. 摩擦点与开放题

8. 本次遇到哪些阻碍？`环境/启动、模型工具调用、文件操作、审批、等待/超时、预算、文档、结果验证、安全/隐私、无、其他`（可多选）。
9. 哪一步最让你犹豫或返工？请只描述操作环节，不要贴任务内容或文件片段。
10. 如果只能改一件事，你最希望改什么？
11. 是否出现让你担心的安全、隐私或未预期行为？`否 / 是（仅描述类别，不写敏感数据）/ 不确定`。

## 6. 访谈提纲（可选）

1. 请回忆刚才最顺利或最困难的一步，具体发生了什么？
2. 你当时预期系统会怎样做？实际结果是什么？
3. 你如何判断是否该批准写入/执行，或是否该停止任务？
4. 哪条文档、错误提示或报告信息最能帮助你？还缺什么？
5. 若只允许改一处，你会改哪一步，为什么？

访谈者记录主题和简短、去身份化摘要；安全事件另按组织流程升级，不把它当成普通满意度问题处理。

## 7. 汇总指标与改进决策

建议每轮至少查看：

- **经独立验证的任务通过率**：`passed / (passed + failed)`；基础设施错误、未执行和缺失验证单列，不混入分母。
- **完成/中断情况**：完成、部分完成、失败、中止与基础设施错误分别计数。
- **耗时与返工**：报告中位耗时、模型轮数和工具错误数；区分等待服务与用户主动操作（若可可靠区分）。
- **安全与控制**：审批请求/批准/拒绝计数、意外行为与隐私疑虑；拒绝审批本身不是负面结果。
- **体验反馈**：单题评分分布、中位数、摩擦点出现次数和访谈主题；保留反例，不只挑正面引语。

每项改动写成可复测记录：`问题 | 基线证据 | 预期变化 | 实际改动 | 复测任务/配置 | 结果 | 后续决定`。如果模型、模板、服务版本、任务或 Harness 同时变化，应把结果视为新基线或做分组分析，而不是归因于单一改动。

## 8. 试点规模与隐私检查

建议先做小规模可用性试点：邀请约 5–8 位不同经验水平的自愿参与者，完成 2–3 个合成/脱敏任务并填写问卷。这个数量只是用来发现明显流程障碍的务实起点，不是统计功效或代表性保证。若要比较群体或发布定量结论，应另行设计样本量、抽样方法和分析计划。

开始前确认：

- [ ] 任务、workspace 和表单都不含真实凭据/客户数据；Shell 测试已在外部隔离环境中设计。
- [ ] 参与者知道目的、字段、访问者、保存期限、退出方式，且同意自愿参与。
- [ ] 默认不采集原始轨迹、提示词、文件内容、工具参数、reasoning 或身份信息。
- [ ] 数据表保存在受限本地或组织批准的存储位置；问卷与任何身份映射表分离。
- [ ] 预先写好安全停止条件、数据删除日期和改进负责人。
- [ ] 结果按任务/流程汇总，不用于给参与者个人排名或绩效打分。

本方案是可试点的内部改进设计，不构成法律、隐私或研究伦理审查意见。涉及员工研究、客户数据或外部发表时，应先遵守组织政策并完成所需审查。
