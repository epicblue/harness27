# Harness27 安全部署操作说明

本页面向需要运行真实任务或评测的操作者，说明 Harness27 提供的保护、明确不提供的隔离，以及如何把它放在更安全的运行环境里。它是操作核对清单，不是可直接复制到所有操作系统的容器配置；网络命名空间和模型服务拓扑必须按实际环境验证。

## 1. 安全边界：保护是什么，不是什么

- **模型客户端**只向字面回环 IP 发 HTTP(S) 请求，拒绝域名、远端地址和重定向，并忽略代理环境变量。这约束 Harness 的 HTTP 客户端，不会限制推理服务自身、系统其他进程或 Shell 的网络。
- **文件工具**把路径解析到指定 workspace 下，拒绝路径越界和其中名为 `.git` / `.harness27` 的目录，并限制单次读写大小。它不是 OS 沙箱；并发目录替换、特殊文件系统和所有硬链接场景并未由应用层约束覆盖。
- **Harness CLI 的 Shell**默认关闭。启用后，模型提出的每条命令都要用户在交互终端检查并确认；命令仍以当前用户权限运行，继承环境变量、可访问 workspace 外资源并可能访问网络。
- **Benchmark Runner 的 Shell**更危险：`--allow-shell` 会自动批准符合 case metadata 的模型命令，没有逐条人工审批；它不是沙箱。敏感约束用例仍禁用 Shell，但这不构成通用安全保证。
- Shell 超时和输出截断不是资源沙箱。POSIX 下 Runner/工具会尝试清理同进程组子进程，但不能保证清理主动脱离进程组的进程；输出先写临时文件，磁盘占用需外部限制。
- 轨迹是审计数据，不是脱敏日志。Harness JSONL 可能包含任务、模型输出、工具调用参数、文件内容和 reasoning；报告及保留的 workspace 也可能包含敏感信息。

## 2. 推荐的默认运行方式

对于一般交互任务，优先采用以下基线：

1. **Shell 保持关闭。**只开放文件工具确实需要的工作流；写入仍需逐次检查 CLI 显示的目标路径和内容。
2. **使用新建、专用的 workspace。**不要把 `$HOME`、整个代码仓库、凭据目录、SSH 配置、云凭据、生产数据或挂载有个人文件的目录作为 workspace。只放本次任务需要的输入副本。
3. **以最小权限运行。**使用没有管理权限的专用用户或受限账号；避免在该进程环境中保留不相关的凭据、云 token、SSH agent 或高权限 socket。
4. **保护运行产物。**`.harness27/runs/`、`.harness27/benchmark/results/` 和保留 workspace 可能包含任务数据。限制读取者，按数据分类/保留策略归档或删除；不要把它们纳入公开日志、工单或 Git。
5. **将“本地调用”与“整机离线”分开管理。**如要求断网，由主机防火墙、容器/虚拟机网络策略等操作系统级控制实现；不要把 Harness 的 loopback 限制视为全机网络隔离。

POSIX 上新建的轨迹与报告文件使用受限文件权限，新建轨迹目录也请求受限权限；已存在目录的权限、非 POSIX 行为和组织存储系统权限仍需运维人员实际检查。权限位不等同于加密或访问审计。

## 3. 需要启用 Shell 时的外部隔离基线

只在任务必须执行命令、并且组织允许运行不可信生成代码时考虑 Shell。运行环境应在启动模型任务**之前**准备好；不要先在宿主机运行命令，再把结果称为隔离。

部署方案至少应考虑以下控制，并在真实目标主机上验证其是否生效：

- **一次性边界：**使用可销毁的容器或虚拟机、专用低权限 UID；运行后销毁实例和临时数据。不要挂载宿主机 home、Docker/Podman 控制 socket、SSH agent 或其他宿主机管理接口。
- **文件边界：**根文件系统尽量只读；只挂载本任务必需的输入和单独的输出目录；对工作区与临时目录施加存储配额。将工作区中的输入视为不可信，不挂载真实生产数据。
- **进程与权限边界：**以非 root 用户运行，去除不需要的能力/权限，采用平台支持的 no-new-privileges、seccomp 或等效控制；为 CPU、内存、进程数、临时文件和运行时长设置操作系统级上限。
- **网络边界：**默认禁止出站网络和宿主机访问。Harness 只接受 loopback 服务地址；因此若模型服务另在容器/主机中，需设计并测试隔离网络命名空间内的本地连接方式。不要为了连模型而把 Harness 指向任意远端 IP；不要假定 `--network=none` 环境能自动访问宿主机上的服务。
- **密钥边界：**启动环境中不注入与任务无关的环境变量或密钥；不允许挂载凭据文件。若本地模型服务确需 API key，限制其权限和生命周期；只要 Shell 可执行，就应假定它能读取 Harness 进程环境中的该 key。
- **运行审计：**记录使用的镜像/VM 基础、隔离策略、Harness commit、模型服务配置和运行时间；日志本身按敏感数据保存。测试完成后核对是否有残留进程、文件、端口或临时数据。

各容器/虚拟机方案的网络、只读挂载和资源限制选项因平台不同而异。本仓库不会创建或校验这些隔离，也不提供通用的“一行安全运行”命令；应由熟悉目标运行时的管理员配置，并用安全团队批准的检查方法验证。

### Agent CLI 与 Benchmark 的审批差异

```bash
# Agent CLI：默认无 shell
python -m harness27 --model local-model --workspace ./task-workspace '任务描述'

# Agent CLI：显式开启后，每次调用仍需交互审批；不因此变成沙箱
python -m harness27 --model local-model --workspace ./task-workspace \
  --allow-shell '任务描述'

# Benchmark：会自动批准 case 允许的模型 Shell 命令；仅可在外部隔离环境中使用
python benchmark/runner.py --case case_03_pytest_repair --allow-shell
```

Benchmark 的工作区唯一、输出截断或 Shell 超时都不是对越权文件访问、联网和资源耗尽的隔离保证。若无法提供上述外部边界，就不要运行 Shell-enabled benchmark。

## 4. 数据与凭据操作

- `HARNESS27_API_KEY` 不写入 Harness 请求轨迹或 benchmark 配置报告；但启用 Shell 时子命令会继承当前环境，模型生成的命令可能读取它。
- Agent 轨迹通常位于 `.harness27/runs/`，记录粒度比 benchmark 报告更详细。Benchmark 报告默认位于 `.harness27/benchmark/results/`；使用 `--keep-workspaces` 会额外保留任务文件。自定义 `--report` 路径也可能在共享目录中。
- 创建共享/长期运行目录前，核查父目录权限、备份、日志采集与保留周期。文件以 `0600` 创建并不会自动保护已有目录、被复制后的文件或系统备份。
- 任务、fixture、工具输出和模型响应都可能包含敏感数据。不要把密钥写进任务/工作区；不要在 issue 或聊天中粘贴未脱敏轨迹、报告和 verifier 输出。
- 评测完成后，按组织的数据保留要求删除临时 workspace、轨迹和报告；只留下已审查、去敏且确有必要的结果摘要。

## 5. 每次运行的核对清单

### 运行前

- [ ] 选用专用 workspace，只包含任务必需文件。
- [ ] 确认 Shell 是否真的必需；若需要，确认外部隔离、网络策略、资源限制和无凭据环境已经生效。
- [ ] 核对 Harness 与模型服务的网络命名空间、回环地址和认证设置。
- [ ] 评测 Shell-enabled case 前确认命令会自动批准，并采用一次性隔离实例。
- [ ] 确认轨迹、报告及 workspace 的位置、权限和保留策略。

### 运行后

- [ ] 检查 Agent 状态、工具事件和生成/修改文件；不要只依据最终自然语言回答。
- [ ] 核对 Shell 子进程、工作区外写入、临时文件和网络访问（若环境允许审计这些行为）。
- [ ] 保护或清理轨迹、报告和 workspace；隔离环境按流程销毁。
- [ ] 若怀疑凭据暴露，立即按组织流程撤销/轮换凭据并检查访问记录。
